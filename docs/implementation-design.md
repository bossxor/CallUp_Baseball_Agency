# 콜업 구현 설계서

**v0.7 · 시제품 기준과 첫 플레이 버전 계획**

[구현 기준 저장소: bossxor/CallUp_Baseball_Agency](https://github.com/bossxor/CallUp_Baseball_Agency) · [게임 설계서](game-design.md)

시제품 기준은 v0.1.10(`f890c91`)이다. TypeScript 코어와 모바일 화면을 Android WebView에 담아 오프라인으로 실행하며, 저장은 기기의 WebView 로컬 저장소를 사용한다. Android UI를 별도로 짜면 플랫폼 화면 제어는 쉬워지지만 같은 게임 흐름을 브라우저와 폰에서 검사하기 어렵다. 현재 구조를 유지하고 오프라인 실행·뒤로 가기·실기기 저장 복구 기준으로 판단한다.

## 1. 구현 범위와 구조

첫 목표는 한국에서 에이전시를 창업해 국내 2군 선수와 첫 고객 계약을 협의하고, 한국·일본·대만·미국 시장을 운영하며 두 번째 시즌 개막까지 진행하는 것이다. 모바일 화면, 주간 보고를 확인하고 다음 주로 넘기는 오프라인 싱글플레이, 기기 내 저장을 기준으로 한다. 배포 대상은 Google Play용 Android 앱이다.

## 2. 주차와 경기

한 저장 파일에는 하나의 달력과 네 시장의 상태가 있다. 주 단위로 진행하되 경기 주차와 시장 등록 기간은 리그 설정에서 관리한다. 주차 처리는 아래 순서를 따른다.

1. 새 주를 열고 예정된 등록과 만료를 먼저 처리한다. 새 주차가 효력일인 등록이 성공하면 해당 주 경기의 기용 후보에 들어간다. 이 순서는 동적 로스터 구현 시 적용한다.
2. 하나의 경기 결과에서 팀 승패와 선수 기록을 함께 집계한다. 팀 순위와 기록 화면은 이 집계를 조회한다. 투구 이닝은 내부적으로 아웃 수로 저장한다.
3. 해당 주의 경기를 집계한 뒤, 최근 기록·부상·선수층에 따라 다음 주 영입 수요를 갱신한다. 예정된 파견 복귀, 면담·협상 회신과 드래프트 결과를 처리한다. 회신 주차는 업무를 시작할 때 저장한다.
4. 주차·등록·수수료·보고함을 한 저장 상태로 기록한다. 실행 중에는 주차 버튼의 중복 조작을 막는다. 해당 주를 저장한 뒤 다음 주를 계산하고, 쓰기 실패 시 마지막으로 읽을 수 있는 주차부터 재시도한다.

경기와 이벤트는 같은 저장과 행동 순서에서 같은 결과가 나오도록 한다. 시제품은 국내 이전 경기의 재현을 위해 `expansionWeek`로 2팀 일정과 10팀 일정을 구분한다. 경기 규칙이나 로스터 계산이 바뀌는 버전부터는 완료 경기 결과를 보관하거나 당시 규칙으로 재현할 수 있게 해, 기존 점수와 보고서 기록이 바뀌지 않도록 한다.

여러 주 진행은 최대 4주다. 시작 시 미결 응답 안건이 있으면 한 주만 진행한다. 시작 뒤에는 스카우트 복귀, 면담 답변, 구단 제안·역제안 회신, 고객 계약 등록, 고객의 1군 등록·지원 점검, 드래프트 결과에서 멈춘다. 일반 경기 결과와 제안 만료만 발생한 주는 중단하지 않는 것을 목표로 한다. v0.1.10 코어는 만료를 포함한 모든 협상 결과에서 멈춘다. 이후 사건마다 **답변 필요**, **일괄 진행 중단**, **연결 화면**을 따로 정의하고 홈·일정·주간 기록에서 그 결과를 읽는다.

### 사건과 후속 업무

- **발생과 표시** — 파견 복귀, 협상 회신과 계약 마감은 예정 주차에 처리한다. 구단 영입 문의나 선수 상담 요청 같은 우발 사건은 경기·로스터·선수 상태를 조건으로 해당 주에 추첨한다. 조건을 충족해도 추첨 결과로 사건이 0건일 수 있다. 사건에는 원인, 대상, 발생 주차, 응답 기한, 실행할 수 있는 선택과 처리 상태를 저장한다. 기한이 가까운 사건을 먼저 표시하고, 일반 소식은 주간 요약으로 모은다.
- **홈과 일정 표시** — 홈에서 가장 가까운 미결 마감과 행동을 가로 뉴스 카드보다 먼저 표시한다. 같은 안건을 사무실 일정에서 다시 찾을 수 있다. 읽은 여부와 응답 여부를 구분하고, 화면에 표시한 마감 주차까지 응답을 허용한다. 뒤로 가면 안건을 연 목록과 위치를 복구한다.
- **이어지는 선택** — 면담 요청, 관심 선수 추가 조사, 구단에 고객 추천을 처리하면 원래 사건과 연결된 회신 일정을 저장한다. 추천할 때는 고객 자격, 구단 역할 수요와 등록 가능 여부를 검사한다. 구단은 다음 주 진행 이후 기존 영입 평가를 사용해 응답하며, 조건에 맞으면 협상 제안을 만든다. 회신은 결과가 나온 주의 보고함에 표시한다.
- **조용한 주** — 새 사건과 예정 결과가 모두 없는 주에는 경기 요약을 표시한다. 여러 주 연속으로 이 상태가 가능하며, 그 사이에도 월드와 주차는 정상적으로 진행된다. 플레이어는 평소처럼 선수 기록이나 시장을 선택해서 열 수 있다. 우발 사건은 주차를 진행할 때 확정하고, 세이브를 불러오거나 같은 주차를 다시 열 때 다시 추첨하지 않는다.
- **선수 지원** — 부상·부진 장기화·역할 변화가 상담이 필요한 상태로 이어지면 고객의 지원 안건을 만든다. 선택 가능한 지원에는 비용과 완료 또는 점검 예정 주차가 붙는다. 선택 결과와 비용을 한 번만 기록하고, 점검 주차에 진행 상황을 보고함에 넣는다. 경기 기용과 복귀 판단은 기존 시뮬레이션 규칙을 따른다.
- **중복과 만료** — 같은 원인과 대상의 미결 사건은 한 건으로 처리하고, 상황이 달라졌을 때 새 사건을 만든다. 같은 처리 요청을 다시 보내도 결과와 후속 회신을 한 번만 기록한다. 지난 제안과 만료 사유는 기록에서 볼 수 있게 하고, 기한 뒤에는 수락할 수 없게 한다.

## 3. 데이터와 계약 규칙

| 데이터 | 필요한 관계와 상태 |
| --- | --- |
| **리그·구단** | 시장, 단계, 달력, 팀 로스터, 포지션별 필요 인원, 등록 가능한 외국인 자리, 가용 예산 |
| **선수** | 현재·잠재 능력, 등록 시장과 소속, 타자·투수 역할, 부상, 선수 선호, 시즌·리그별 경기 기록 |
| **에이전시 계약** | 고객, 기간, 수수료율, 관계, 상담 기록. 선수의 구단 소속과 별도 관리 |
| **구단 계약** | 대상 선수, 구단, 효력 주차, 기간, 보장 금액과 옵션, 보유권과 해외 진출 허가 |
| **제안·회계** | 제안 ID와 시한, 시장과 등록 예정 주차, 예상 역할, 협상 상태. 수수료는 구단 계약 ID를 기준으로 한 번 기록 |

신인 지명 결과는 한국 시장에서만 처리한다. 지명된 선수의 첫 구단 계약은 해당 지명 구단과 협상한다.

구단은 포지션별 필요 인원, 예산과 등록 가능 여부를 평가해 후보에게 제안한다. 자유계약 선수는 등록 조건을 충족하는 구단과 계약할 수 있다. 해외 진출 허가가 있는 소속 선수도 외부 제안을 협상할 수 있으며, 등록 전까지 현재 소속을 유지한다. 마이너에서 메이저로 올라가는 경우에는 동일 미국 구단 조직 내 등록 단계가 바뀐다.

계약 종류를 구분한다. 같은 구단과의 연봉·계약 갱신은 기존 등록 자리를 유지하고 연봉 조건만 갱신한다. 새 구단 등록은 외국인 등록 자리와 보장 연봉 예산을 함께 예약한다. 두 경우 모두 확정할 때 자격·시한·선수 동의·예산을 검증한다. 자리 공백과 외국인 등록 여유는 서로 별개로 본다.

동적 시장 구현 시 효력 주차 시작에 예약을 소진하고 소속과 회계를 함께 반영한다. 등록할 수 없으면 같은 주 진행을 끝까지 허용하고 실패 결과를 기록한다. 예약을 해제하고 기존 소속과 자금은 유지한다. 종료된 경쟁 제안은 자동 재개하지 않으며 자격이 있으면 새 추천을 보낼 수 있다. 현재 소속 시장과 출신 시장을 각각 저장하고, 등록 후 선수 목록은 현재 소속을 기준으로 표시한다. 수수료는 효력이 발생한 구단 계약 ID당 한 번만 기록한다. 새 계약과 갱신은 계약서의 보장액과 적용 수수료율을 저장하고, 인센티브와 미확정 옵션을 초기 보장액에서 제외한다.

시제품 초기 자금은 1,500만 원이다. 파견은 국내 50만 원·2주, 해외 120만 원·3주이며 정밀 조사는 50만 원과 1주를 더 쓴다. 추가 조사는 30만 원·1주이고 파견 자리 하나를 사용한다. 파견 자리는 고객 수에 따라 1~3개다. 비용은 예약을 저장할 때 한 번만 차감한다. 잔액이 부족하면 해당 예약을 만들지 않는다. 현지 네트워크 투자와 지원의 장기 효과는 첫 경로의 선택이 성립함을 확인한 뒤 정한다.

## 4. 스카우트 보고서와 종이 전환

- **파견 완료** — 지역, 조사 유형과 복귀 주차를 저장한다. 복귀 주차를 처리할 때 파견당 보고서 한 건과 도착 알림을 만든다. 보고서는 조사 결과의 스냅샷이며, 후보 ID와 표시 순서, 관찰 기간의 경기 기록과 출전량, 실력·잠재력 추정 범위, 관찰 근거와 의견을 보관한다. 실제 잠재력은 시뮬레이션 데이터에서 관리한다.
- **보고서 읽기** — 첫 장을 열고, 좌우 스와이프나 이전·다음 버튼으로 선수 한 명씩 확인한다. 모바일에서 본문을 세로로 스크롤할 때 페이지가 바뀌지 않도록 제스처 방향을 구분한다. 첫 장과 마지막 장에서는 이동 가능한 방향만 활성화한다. 동작 줄이기 설정에서는 전환 애니메이션 없이 같은 페이지로 이동한다.
- **보고서 활용** — 각 페이지에서 관심 선수 등록, 추가 조사, 면담 요청으로 연결한다. 보고서를 다시 열면 복귀 시점의 내용과 마지막으로 읽은 장을 불러온다. 후보가 없는 파견에는 조사 결론 한 장을 표시한다. 보고서 제목, 현재 장과 전체 장 수, 이전·다음 버튼에 접근성 레이블을 제공한다.
- **Android 검증** — 작은 세로 화면에서 정보와 터치 영역이 겹치지 않는지, 기기의 뒤로 가기로 사무실에 돌아가는지, 화면을 나갔다 돌아와도 보고서와 읽은 위치가 복구되는지 확인한다.

## 5. 구현 순서와 검증 기준

### 첫 시제품

기준 버전의 홈 → 파견 → 주차 진행 → 보고서 → 면담 → 고객 계약을 작은 세로 화면에서 확인한다. Android에서 오프라인 실행, 보고서 뒤로 가기, 마지막 페이지와 미결 업무 복구를 처음부터 검증한다. 새 화면은 [게임 설계서의 화면 기준](game-design.md#7-첫-플레이-버전의-화면과-완료-기준)에 따라 터치 순서와 목록 복귀를 비교한다.

### 첫 플레이 버전

| 순서 | 구현 단위 | 완료 시 확인할 것 |
| --- | --- | --- |
| **1** | 홈 동선, 기존 국내·대만 경로와 저장 보호 | 320px 세로 화면의 홈에서 마감, 선수 상세, 돌아온 보고서, 응답 가능 제안에 직접 접근한다. 안건이 0건인 주와 여러 건 겹친 주, 뒤로 가기와 재실행을 비교한다. 오류가 난 저장은 덮어쓰지 않는다. |
| **2** | 국내 콜업·연봉 협상, 대만·일본의 추천·비교·등록 | 국내 고객의 역할과 연봉을 보고 선택한다. 대만과 일본 제안의 응답 가능 기간이 겹친 사례로 조건을 비교한다. 마감 주의 수락, 다음 주 만료, 등록 실패 시 예약 해제, 등록 재시도와 중복 수수료 방지를 검증한다. |
| **3** | 실제 로스터, 네 시장 집계, 국내 드래프트 | 각 시장 경기와 순위의 합계가 맞는다. 같은 경기에서 팀과 선수 기록이 일치한다. 국내 드래프트 지명 결과가 첫 구단 계약 선택으로 이어진다. |
| **4** | 오프시즌과 시즌 2, Android 저장 이전 | 미결 협상과 파견이 있는 세이브를 다른 설치에서 불러온다. 다음 시즌에는 새 기록을 집계하고 고객 계약·이력은 이어간다. |

현재 자동 검증은 기본 시드 `20261119`와 조건을 설정한 저장으로 실행한다. 출시 검증에도 같은 방식으로 시드·행동 순서·기대 주차를 남긴다. 대만 보고서의 후보 0명·1명·복수, 두 구단 제안이 동시에 열리는 상태, 마지막 응답 가능 주차, 등록 직전 재실행과 중복 성공 처리, 기존 2팀 저장의 10팀 전환을 각각 검증한다.

현재 저장기는 성공한 쓰기 전에 읽기와 같은 크기·형식 제한을 검사하지 않는다. 출시 전, 성공 처리한 세이브는 즉시 다시 열 수 있어야 하고 실패 시 원본을 보존해야 한다. 지원하지 않는 버전과 손상된 저장을 구분해 표시한다. 새 게임이나 가져오기로 교체할 때는 원본 보관과 명시적 확인이 필요하며, 실제 Android에서 다운로드와 가져오기를 검증한다.

## 6. Android와 Google Play 출시 준비

릴리스 단위마다 수정 경로와 검증을 함께 기록한다.

| 작업 | 파일과 검증 |
| --- | --- |
| 홈·선수·영입 동선 | `src/main.ts`, `src/style.css`. 기존 세이브에서 카드 한 번으로 상세를 열고, Android 뒤로 가기로 목록 위치를 복구한다. |
| 주차 처리와 저장 | `src/game.ts`, `src/main.ts`, `tests/game.test.mjs`. 두 번째 주 계산 또는 저장에 실패하면 첫 주가 복구되어야 한다. 실패를 없앤 뒤 다시 진행한 결과는 같은 횟수의 단일 주차 진행과 일치해야 한다. |
| 등록·회계 | `src/club-deals.ts`, `src/game.ts`, `tests/game.test.mjs`. 선수별 제안과 안정적인 계약 ID를 저장한다. 두 선수가 마지막 자리를 요청하는 경우, 등록 실패와 후속 주차 진행, 성공 후 재실행을 검증한다. |
| 리그·경력 | `src/korea.ts`, `src/clubs.ts`, `src/game.ts`. 각 시장의 경기 시작과 등록 창, 시즌 마감, 신인 계약 자격과 이월 상태를 확정한 뒤 구현한다. 선수 타석은 실제 소속 구단의 해당 경기에서만 집계한다. 기존 시즌 기록, 계약, 구단명을 함께 복구하는 세이브를 검사한다. |

각 단계에서 `npm test`를 실행한다. 현재 기기용 APK는 `npm run android`로 만든다. AAB 서명·검증 명령과 출시 세이브 복원 경로는 Google Play 제출 전에 별도 검증한다.

첫 플레이 버전에서 실제 Android 기기로 오프라인 실행, 저장 후 재시작, 뒤로 가기, 작은 화면에서의 조작을 확인한다. 제출용 Android App Bundle(AAB)과 앱 서명 절차를 준비한다. 목표 API 수준, Play Console의 앱 콘텐츠·데이터 보안 항목은 실제 제출 시점의 기준을 확인한다. 스토어에 쓸 아이콘·스크린샷·게임 소개 문구는 콜업의 실제 화면과 자체 자산을 기준으로 준비한다.
